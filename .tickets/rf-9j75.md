# Phase 1.5: Rate limiting and cost guardrails

## Why
The link is the only secret and the endpoint is public, so guessing and hammering must be bounded, and Durable Object cost must not be able to run away (people who deploy on a paid Cloudflare plan are the worry; free plan simply stops at its limits).

## What was done
- Cloudflare Rate Limiting bindings in wrangler.jsonc: `LIMIT_IP` (60 req/60s per `CF-Connecting-IP`, also applied to /api BEFORE auth to bound token guessing) and `LIMIT_GLOBAL` (300 req/60s circuit breaker on the PUBLIC fetch path only, so a fetch flood cannot lock the owner out of uploading). Bindings are optional in code and fail open if missing/erroring. The binding only supports 10s or 60s periods and is per-location and approximate (a deterrent, not accounting).
- Quotas enforced in the DO: max file size (50 MiB default, hard ceiling 100 MiB = Workers body limit), total stored bytes (2 GiB), uploads/day (200), max TTL (7d), purge grace (7d). All are vars in wrangler.jsonc parsed by packages/worker/src/config.ts.
- Cost design: one DO instance, no WebSockets/timers, alarm only when something is due; with that, duration cost is ~324k GB-s/month worst case, under the 400k GB-s included on paid; requests are the only exposure and scale linearly (see docs/PLAN.md section 5).

## Acceptance Criteria

- [x] Rate limiters run before any DO call (tests with injected limiter stubs assert the DO is untouched).
- [x] One test exercises the REAL limiter binding (single IP eventually gets 429, another IP unaffected).
- [x] Limits are configurable via wrangler vars and documented in the README.
- [x] docs/PLAN.md documents the cost model with Cloudflare's published pricing (checked 2026-10-02) and the caveat that the limiter is approximate.
